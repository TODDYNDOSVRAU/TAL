Findings (static RE, 2026-11-03):

- **NAND BAD BLOCKS IN ROOTFS1, PERMANENT 2026-11-08**: factory-bad NAND blocks 359-364 (phys 0x2ce0000-0x2d80000) sit inside `rootfs1`'s range (0x20000-0x2da0000) - confirmed by `nand_read_bbt` printing them at every single boot since the start of this project, and by `rootfs1`'s own JFFS2 bootfs read always failing with "ERROR: A JFFS2 directory entry for vmlinux.lz was not found." whenever CFE picks it as "latest". `rootfs1` can never hold a bootable kernel. Fix in progress: get into CFE's `c` config menu and set `Boot image (0=latest, 1=previous)` to `1` so it boots `rootfs2` (the one that actually has v25's PMC-fix kernel) regardless of the seq# comparison - this is pure CFE NVRAM config, not a flash write.

- **CFE PARTITION-TARGETING LIMITATION, IMPORTANT FOR FUTURE SESSIONS 2026-11-08**: CFE's recovery web-upload page AND its CLI `w`/`ws` commands always write starting at flash offset 0 (`rootfs1`) - confirmed empirically across many upload attempts (ROOTFS1 Seq# climbed 83->86 while ROOTFS2 Seq# never moved from 083), regardless of which seq# is higher or how the recovery prompt was reached (JFFS2-read-failure fallback vs. a clean autorun-interrupt keypress - both land on the same rootfs1-only write path). There is no known CFE command to target `rootfs2` directly. `rootfs1` also has permanently bad NAND blocks (block 359-364, phys 0x2ce0000-0x2d80000, confirmed via `nand_read_bbt` at every single boot since the start of this project) inside its overall partition range - CFE's own JFFS2 scanner (which treats the whole `rootfs1` partition as one flat region, unaware of our Linux-side nested sub-partitioning) usually can't get past them, giving `ERROR: A JFFS2 directory entry for vmlinux.lz was not found.` and dropping to recovery - **except this is not 100% deterministic**: the 2026-11-08 v25 test actually DID boot successfully from `rootfs1` once, past those same bad blocks, so treat rootfs1 as "usually broken, sometimes works" rather than "always broken" - still prefer rootfs2 for anything that needs to be reliable. The CFE console (`c` command at the `CFE>` prompt to enter the interactive config wizard, fields in a fixed order ending in `Boot image (0=latest, 1=previous)`) can force CFE to always BOOT `rootfs2` regardless of seq# (set that field to `1`) - this is a pure NVRAM config change, confirmed to persist and work reliably. Also explored: `r [hostip:]filename` + `go [address]` can load a file via TFTP into RAM without any flash write, but `r` only loads bytes (returns byte count as "command status") and does not auto-execute even when given our CFE-header+LZMA-wrapped image - the RAM load address it uses is unknown (would need to RE `cferam.000`, no source available) so `go` was never attempted. ## RESOLVED 2026-11-08: custom Linux 6.12.8 kernel (new "runner" driver port) now boots on real hardware

Three root causes, found by bisecting with a custom ARM trampoline stub (writes raw bytes to the BCM6345 UART at `0xfffe8600`/`0xfcfe8600` before/after MMU-on) plus temporary `dbg_phys`/`dbg_virt`/`dbg_hex32` print macros spliced into `head.S`/`head-common.S` at successive checkpoints (letters `0123` pre-MMU, `ABCDE` around page-table/MMU-enable, hex dumps of r2 and the FDT magic). Each hypothesis was tested on the real router via CFE's `.w` upload page, never flashed by the assistant itself.

1. CFE's LZMA decoder silently returns success on a truncated/garbage decompression when the LZMA_ALONE header declares "unknown size" (0xFFFFFFFFFFFFFFFF) — our Python `lzma.compress(..., format=FORMAT_ALONE)` always writes that sentinel even when size is known. Fix: patch the 8-byte size field post-compression (script `fix_lzma_header.py`).
2. CFE's own ROOTFS Seq# comes from the raw JFFS2 **dirent node's binary "version" field** for the `cferam.000` entry, not from the filename's digits (that's a separate, unrelated userspace mechanism in `board.c`). Also, `cferam.000` must be stored **uncompressed** (`mkfs.jffs2 -m none`) or CFE's minimal boot-time JFFS2 reader can't read it. Fix: `patch_dirent_version.py` directly patches bytes [16:20) of the dirent and recomputes its CRC32 (`zlib.crc32(data,0xffffffff)^0xffffffff`, the JFFS2-internal convention — different from the WFI trailer's CRC convention at the very end of the `.w` file, which uses seed 0xFFFFFFFF with **no** final XOR).
3. Kernel booted into total silence after the jump from CFE. Two stacked bugs:
   a. `CONFIG_DEBUG_LL`/`CONFIG_DEBUG_KERNEL`/`CONFIG_DEBUG_BCM63XX_UART` were off, so nothing could print before Device Tree parsing — enabling them revealed "Error: invalid dtb and unrecognized/unsupported machine ID" (CFE passes legacy ATAGS in r2, not a DTB pointer; `CONFIG_ARM_APPENDED_DTB` auto-fixup only lives in the unused zImage decompressor stub, since CFE does its own external LZMA decompression and jumps straight into the raw kernel). Fixed with a small hand-written ARM trampoline (`dtb_stub_debug.S`) placed in the kernel's free `TEXT_OFFSET` gap, setting r1=0xffffffff (DT sentinel) and r2=computed DTB physical address before jumping to the real entry.
   b. Even with the stub reaching the kernel (confirmed via a literal `"STUB-OK"` UART print), everything after was still silent. Root cause: **the stub's hardcoded physical jump/DTB addresses were computed using the kernel's virtual link base (0xc0008000) as if it were the physical load address.** This board's real physical RAM starts at 0x00000000 (confirmed via `bcm963138-dsl-ac88u.dts`'s `memory@0 { reg = <0x0 0x20000000>; }`), and CFE's own boot log address ("`Entry at 0x00007f80`") was the real, low physical address all along — not a truncated display of the high one. ARM's `head.S` is position-independent (computes its own `PHYS_OFFSET` at runtime via `adr_l`), so once the stub's jump target was changed to the correct low address (`KERNEL_ENTRY=0x00008000`, i.e. `PHYS_OFFSET(0)+TEXT_OFFSET(0x8000)`), the kernel ran clean through page-table setup and MMU-enable (checkpoints A–E all printed).
   c. One more bug after that: `fdt_check_header()` returned `-FDT_ERR_ALIGNMENT` (-19) because the DTB's placement in the combined stub+vmlinux+dtb blob landed on a physical address that was only 4-byte aligned, not the 8-byte alignment libfdt requires. Fixed by padding the blob so the DTB offset rounds up to the next 8-byte boundary. After that fix: `fdt_check_header()` returns 0, `setup_machine_fdt` resolves the DT-only "Generic DT based system" machine descriptor, and the kernel prints `Booting Linux on physical CPU 0x0` / `Linux version 6.12.8` for the first time ever in this project, continues through L2C-310 cache init, the custom `bcm63138_runner` driver's `data_path_init()`, and only panics at the very end on `VFS: Unable to mount root fs` — expected, since this test image has no real rootfs/initramfs configured yet.

**How to apply:** the debug-stub/checkpoint technique (raw UART pokes spliced into `head.S`/`head-common.S`, removed before a "real" build) is the fastest way to bisect any future silent-hang-after-CFE-jump bug on this board. When computing any physical address for a custom bootloader-trampoline on an ARM board, always verify the DTS's actual `memory@0` reg value — never assume it matches the kernel's virtual link address high bits.

## 2026-11-07 — Descoberta: Seq# vem da VERSÃO do node JFFS2, não do nome do arquivo

Teste real da v4 (cferam renomeado pra "090") deu `ROOTFS1 Seq#: 000` de novo — IGUAL ao v3! O usuário confirmou (com razão, me cobrou) que realmente gravou o arquivo certo. Investigando: o `mkfs.jffs2` sempre atribui **version=0** ao dirent do primeiro arquivo criado numa árvore nova, INDEPENDENTE do nome do arquivo. Ou seja, renomear pra "090" não mudava nada que o CFE realmente lê — a leitura da sequência usa o campo **version do node JFFS2 do dirent**, não os dígitos do nome do arquivo (o nome "cferam.XXX" é só convenção usada pelo driver do KERNEL rodando, não pelo scanner da CFE).

Tentei usar `mkfs.jffs2 -i <base>` (modo incremental) pra gerar versões mais altas automaticamente, mas ele cria um NOVO inode (ino diferente) em vez de atualizar o existente, e a versão do dirent continua em 0 — não resolve.

**Correção real**: fiz patch binário direto no `bootfs.jffs2` — mudei o campo `version` do DIRENT do `cferam.000` (offset 16 dentro do node, no byte 16 do arquivo já que é o primeiro node) de 0 pra 90, e recalculei o `node_crc` (bytes 0-32) com a fórmula certa do JFFS2 (calibrada contra o `cferam.000` real do stock): `zlib.crc32(dados, 0xffffffff) ^ 0xffffffff` sobre os 32 bytes do node (magic+nodetype+totlen+hdr_crc+pino+version+ino+mctime+nsize+type+unused+name_crc fica de fora, só node_crc muda). `hdr_crc` e `name_crc` não precisam mudar (cobrem outros campos que não mudaram).

Script: `scratchpad/patch_dirent_version.py`. Validado com `jffs2dump -c` (mostra version=90, sem erro de CRC) e recriado o `.w` completo como v5.

`DSL-AC88U_teste_driver_runner_v5.w`, sha256 `55e9d9991e97506e798a4f566a4dcdc27534c1a9a6ffa07b537c6708c66130c8`, verificado exaustivamente (LZMA ok, UBI intacto, trailer válido, JFFS2 limpo, dirent cferam.000 com version=90 confirmado).

## 2026-11-07 — CONFIG_DEBUG_LL funcionou! Causa raiz EXATA do travamento mudo encontrada

A v6 (com DEBUG_LL) revelou a mensagem de erro real pela primeira vez:
```
Error: invalid dtb and unrecognized/unsupported machine ID
  r1=0x0000270a, r2=0x00000100
  r2[]=05 00 00 00 01 00 41 54 01 00 00 00 00 10 00 00
Available machine support:
ID (hex)  NAME
ffffffff  Generic DT based system
Please check your kernel config and/or bootloader.
```

**Causa raiz confirmada**: `r2[]` começa com `05 00 00 00 01 00 41 54` — isso é literalmente um `ATAG_CORE` (tag=0x54410001, size=5), ou seja, a **CFE está passando uma lista ATAGS clássica em r2**, não um ponteiro pra Device Tree. O kernel (DT-only, só tem a entrada genérica "Generic DT based system" ID=0xffffffff) tenta validar r2 como DTB (falha, não é magic 0xd00dfeed) e r1 como ID de máquina legado (falha, 0x270a não bate com nada) — e recusa bootar.

**Por que isso não acontecia com o kernel original (3.4.11)**: aquele kernel usa board files legados (não é DT-only), aceita o r1/ATAGS da CFE diretamente, sem precisar de DTB nenhum.

**Por que `CONFIG_ARM_APPENDED_DTB`/`CONFIG_ARM_ATAG_DTB_COMPAT` (já ligados) não ajudam**: confirmei no código-fonte que essa lógica (procurar um DTB colado depois do kernel, converter ATAGS) existe SÓ dentro do stub de auto-descompressão do zImage (`arch/arm/boot/compressed/`), NÃO no kernel real (`arch/arm/kernel/head.S`/`head-common.S`). Como a CFE faz a descompressão LZMA ela mesma (função que já mapeamos, `FUN_00f1eca0`/decompressor) e pula direto pro kernel JÁ descomprimido, esse stub nunca roda — então nada nunca diz pro kernel onde está o DTB que anexamos.

**Correção planejada (ainda não implementada)**: escrever um pequeno "stub" em assembly ARM (poucas instruções) que:
1. Carrega `r2` = endereço do DTB (calculado em build-time = endereço de carga do kernel + tamanho exato do `vmlinux.bin`).
2. Zera `r1` e `r0`.
3. Pula (`ldr pc, =0xc0008000`) pro entry point REAL do kernel.

Esse stub fica carregado logo ANTES do endereço 0xc0008000 (na folga de 32KB que o `TEXT_OFFSET` do kernel ARM deixa de propósito pra esse tipo de uso), com `load_addr` e `entry_addr` do nosso header de 20 bytes apontando pro INÍCIO do stub (não mais direto pro kernel) — o `vmlinux.bin` em si continua carregado exatamente em `0xc0008000`, sem precisar relinkar nada.

Vou implementar isso agora.
